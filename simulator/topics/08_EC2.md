## Glossario: i servizi che incontrerai in questo documento

- **EC2 (Elastic Compute Cloud)** — una macchina virtuale nel cloud. Come avere un computer (Linux o Windows) che gira nei data center di AWS. Ci puoi installare quello che vuoi. Paghi per il tempo in cui è accesa e per la potenza che scegli (CPU, RAM). Esistono diverse "famiglie" di istanze: alcune ottimizzate per calcolo, altre per memoria, altre per storage.

- **AMI (Amazon Machine Image)** — è la "foto" del sistema operativo e del software preinstallato. Quando lanci un'istanza EC2, scegli un AMI che definisce cosa c'è dentro. Come scegliere un'immagine ISO per installare un sistema operativo, ma già pronta all'uso.

- **Instance Store** — storage fisicamente attaccato al server che ospita la tua istanza EC2. Velocissimo (è un disco locale), ma **temporaneo**: quando spegni l'istanza, i dati spariscono. Pensalo come la RAM di un computer — veloce ma volatile.

- **Auto Scaling Group (ASG)** — un gruppo di istanze EC2 che cresce e si riduce automaticamente in base al carico. Se il traffico aumenta, lancia nuove istanze. Se diminuisce, le spegne. È come avere un team di camerieri in un ristorante: nei momenti di punta ne chiami di più, quando è tranquillo ne mandi a casa.

- **Launch Template** — il "modello" che dice all'ASG come creare le nuove istanze: quale AMI usare, che tipo di istanza, quali security group, quale storage. Come un ordine precompilato al ristorante.

- **Spot Instance** — capacità EC2 inutilizzata che AWS vende a prezzo scontato (fino a -90%). Il trucco: AWS può riprendersela con 2 minuti di preavviso se serve a qualcun altro. Come un biglietto aereo last-minute: costa pochissimo ma potresti essere "bumpato" dal volo.

- **Reserved Instance (RI)** — ti impegni a usare un certo tipo di istanza per 1 o 3 anni in cambio di uno sconto (fino a -72%). Come un abbonamento annuale alla palestra: paghi meno al mese ma sei vincolato.

- **Savings Plan** — simile alle RI ma più flessibile. Ti impegni a spendere un certo importo all'ora per 1-3 anni, e lo sconto si applica automaticamente a EC2, Lambda, Fargate. Come un abbonamento "all-inclusive" che copre palestra, piscina e sauna.

- **Placement Group** — un modo per controllare DOVE fisicamente vengono posizionate le tue istanze EC2 nei data center. Cluster (vicine per bassa latenza), Spread (separate per resilienza), Partition (gruppi isolati).

- **Elastic Fabric Adapter (EFA)** — un'interfaccia di rete speciale per workload HPC e machine learning che ha bisogno di throughput di rete superiore al normale TCP. Come una corsia preferenziale in autostrada per i camion pesanti.

## Panoramica Compute su AWS

Il PACKT introduce EC2 come *"il primo servizio mai rilasciato da AWS. Amazon EC2 è un servizio fondamentale che fornisce capacità di calcolo ridimensionabile nel cloud."*

Il Dojo aggiunge: *"EC2 è considerato il building block base in AWS — è usato in quasi ogni servizio!"*

### Scelta del Servizio Compute (dal PACKT)

Il PACKT elenca le opzioni compute e quando usarle:

| Servizio | Quando usarlo |
|---|---|
| **Amazon EC2** | Hosting web app, backend services, batch processing, WordPress, microservizi, data analytics |
| **Elastic Beanstalk** | Deploy e gestione app web/API senza gestire i server. Java, Python, Node.js, PHP |
| **Amazon ECS** | Applicazioni containerizzate con Docker, microservizi, batch processing |
| **Amazon EKS** | Cluster Kubernetes per applicazioni containerizzate |
| **AWS Fargate** | Container senza gestire infrastruttura, scaling rapido e semplice |
| **AWS Batch** | Grandi volumi di dati, task compute-intensive, pipeline analytics, rendering, simulazioni |
| **AWS Lambda** | Event-driven, risposte a cambiamenti dati, richieste HTTP, messaggi da altri servizi |

> **Tip esame (PACKT)**: *"There will be questions in the exam where you will need to decide the best service to use for a specific type of workload, so understanding the key differences between them is critical."*

### VM vs Container (dal PACKT)

Il PACKT spiega la differenza:
- **VM**: emulazione software di un computer fisico, include un intero OS stack (kernel, librerie, binari). Forte isolamento ma overhead di risorse
- **Container**: ambiente runtime leggero e portabile. Condivide il kernel dell'OS host. Più efficiente, startup veloce, ideale per microservizi e CI/CD

## Tipi di Istanze EC2

### Famiglie di Istanze (dal PACKT e Dojo)

| Famiglia | Ottimizzata per | Casi d'uso (PACKT + Dojo) |
|---|---|---|
| **General Purpose** (T, M) | Bilanciamento compute/memory/networking | Web server, ambienti dev, database piccoli-medi |
| **Compute Optimized** (C) | Alta potenza CPU | HPC, batch processing, media transcoding, gaming server, ML inference (Dojo) |
| **Memory Optimized** (R, X) | Grandi dataset in memoria | Database in-memory, analytics real-time, caching su larga scala |
| **Storage Optimized** (I, D) | Accesso ad alta performance allo storage locale | NoSQL database, data warehousing, log processing, decine di migliaia di IOPS (Dojo) |
| **Accelerated Computing** (P, G) | Hardware specializzato (GPU) | ML inference, rendering grafico, video processing |
| **HPC Optimized** | Calcolo ad alta potenza, networking a bassa latenza | Ricerca scientifica, modellazione finanziaria, simulazioni ingegneristiche |

### Burstable vs Standard (dal PACKT)

Il PACKT fa una distinzione importante:

**Burstable Instances** (prefisso `t`, es. t3.micro):
- Per workload con utilizzo CPU variabile
- Accumulano **CPU credits** durante periodi di bassa attività
- Usano i credits durante burst di domanda più alta
- *"È essenziale monitorare i CPU credits per assicurare performance consistenti perché quando i credits finiscono, vedrai degradazione delle performance (standard mode) o costi aumentati (unlimited mode)"*

**Standard Instances** (M, C, R, ecc.):
- Performance CPU fissa basata sulla dimensione selezionata
- Non richiedono gestione dei CPU credits
- Per workload steady-state o che richiedono performance prevedibili

### Nitro-based Instances (dal Dojo)

Il Dojo menziona le istanze Nitro: *"Il Nitro System fornisce capacità bare metal che eliminano l'overhead di virtualizzazione. Quando monti volumi EBS Provisioned IOPS su istanze Nitro-based, puoi provisionare da 100 IOPS fino a 64,000 IOPS per volume, rispetto a solo 32,000 su altre istanze."*

### Graviton (dal PACKT Cap.14)

Il PACKT menziona: *"AWS offre il suo tipo di processore, Graviton. Alcuni tipi di istanza vengono con processori Graviton, e questi possono offrire performance migliori rispetto ai loro equivalenti Intel."*

## AMI — Amazon Machine Images (dal PACKT e Dojo)

Il PACKT spiega: quando lanci un'istanza EC2, selezioni un AMI che definisce la configurazione software iniziale e il sistema operativo. AWS offre AMI pre-configurate per Amazon Linux, Ubuntu, Windows Server, ecc.

Il Dojo dettaglia i componenti di un'istanza EC2 step by step:
1. **Scegli AMI** — contiene OS, impostazioni, applicazioni. Non può essere modificata dopo il lancio
2. **Scegli instance type e size** — determina CPU, RAM, velocità di rete. Puoi modificare il tipo anche dopo il lancio (**right sizing**)
3. **Configura impostazioni** — numero istanze, spot/on-demand, VPC/subnet, IP pubblico, placement group, IAM role, shutdown behavior, termination protection, user data
4. **Aggiungi storage** — volume EBS automatico per OS, puoi aggiungerne altri
5. **Aggiungi tag** — per identificazione e classificazione
6. **Configura Security Groups** — firewall per l'istanza
7. **Key pair** — per accesso sicuro. *"Non c'è modo di riassociare un'altra key pair dopo il lancio"* (Dojo)

### Instance Store vs EBS (dal PACKT e Dojo)

| Caratteristica | Instance Store | EBS |
|---|---|---|
| Tipo | Storage fisicamente attaccato all'host | Storage network-attached |
| Persistenza | **Temporaneo** — dati persi quando l'istanza si ferma | **Persistente** — dati sopravvivono a stop/delete |
| Performance | I/O più alto (fisicamente attaccato) | Buono, ma con latenza di rete |
| Creazione | Solo al provisioning dell'istanza | In qualsiasi momento |

Il Dojo aggiunge un dettaglio importante sulle performance: *"Se hai bisogno di IOPS davvero alti, bassa latenza, e i dati non devono necessariamente persistere, i volumi instance store su tipi di istanza specifici potrebbero essere preferibili ai volumi EBS Provisioned IOPS. I volumi instance store sono fisicamente attaccati alle istanze EC2, quindi le istanze possono accedere ai dati molto più velocemente."*

> **Tip esame (PACKT)**: *"It is important to remember that any data stored on an instance store volume is lost when the instance is stopped, whereas data on an EBS volume persists."*

## Opzioni di Acquisto EC2

### Panoramica (da Kimiko)

Kimiko spiega le opzioni dalla console: *"Quando sei nella management console EC2 e lanci un'istanza, stai tipicamente facendo quello che si chiama acquistare un'istanza On-Demand. Ma ci sono molte opzioni per l'acquisto di risorse EC2."*

### Tabella Completa (dal Dojo)

| Opzione | Come funziona | Sconto | Ideale per |
|---|---|---|---|
| **On-Demand** | Paghi al secondo/ora per ogni istanza in esecuzione. Nessun impegno | Nessuno | Workload imprevedibili, test, dev |
| **Savings Plans** | Impegno su un importo USD/ora per 1 o 3 anni. **Compute SP**: si applica a EC2, Fargate, Lambda indipendentemente da famiglia/size/AZ/region/OS. **EC2 Instance SP**: più economico ma limitato a una famiglia in una region | Fino a 72% | Workload steady-state con flessibilità |
| **Reserved Instances** | Impegno su configurazione specifica (tipo, region) per 1 o 3 anni. **Standard RI**: sconto massimo, vendibili su Marketplace. **Convertible RI**: puoi cambiare attributi. **Scheduled RI**: per schedule ricorrenti | Fino a 72% | Workload prevedibili, steady-state |
| **Spot Instances** | Capacità EC2 inutilizzata a prezzo ridotto. L'istanza viene fermata/terminata con **2 minuti di preavviso** quando il prezzo sale | Fino a 90% | Batch processing, analytics, workload interrompibili |
| **Dedicated Hosts** | Host fisico dedicato. Supporta BYOL (Bring Your Own License) | Variabile | Compliance, licensing per-socket/per-core |
| **Dedicated Instances** | Istanze su hardware single-tenant. Isolamento fisico a livello hardware | Variabile | Isolamento, compliance |
| **Capacity Reservations** | Riserva capacità in una AZ specifica. Nessun impegno di durata | Nessuno | Garanzia di disponibilità |

### Standard RI vs Convertible RI (dal Dojo)

| Caratteristica | Standard RI | Convertible RI |
|---|---|---|
| Si applica a tutte le AZ nella region | Sì | Sì |
| Condivisibile tra account (consolidated billing) | Sì | Sì |
| Cambiare AZ, instance size (Linux), networking type | Sì | Sì |
| Cambiare instance family, OS, tenancy, payment option | **No** | **Sì** |
| Beneficiare di riduzioni di prezzo | **No** | **Sì** |
| Comprare/vendere su Marketplace | **Sì** | **No** |

### Dedicated Hosts vs Dedicated Instances (dal Dojo)

| Caratteristica | Dedicated Hosts | Dedicated Instances |
|---|---|---|
| Billing | Per-host | Per-instance |
| Visibilità socket, core, host ID | Sì | No |
| Host e instance affinity | Sì (deploy consistente sullo stesso server fisico) | No |
| Targeted instance placement | Sì | No |
| BYOL | Sì | No |

> **Nota da Kimiko**: *"La maggior parte di queste opzioni riguarda il risparmio. Ma poi arriviamo a qualcosa come il Dedicated Host e si tratta di spendere di più. È importante prima dell'esame essere ben armati con queste diverse opzioni."*

> **Nota da Kimiko sul billing**: *"Per molto tempo le risorse compute venivano addebitate su base oraria. Amazon è passata all'accumulo di addebiti al secondo, il che aiuterà a ridurre le bollette AWS per molti."*

## Placement Groups (dal Dojo)

Il Dojo descrive tre strategie di placement:

| Strategia | Come funziona | Caso d'uso |
|---|---|---|
| **Cluster** | Istanze vicine nella stessa AZ. Può estendersi su VPC peered nella stessa Region | Bassa latenza, alto throughput di rete |
| **Partition** | Istanze distribuite su partizioni logiche che non condividono hardware. Max 7 partizioni per AZ, multi-AZ | Riduce la probabilità di failure hardware correlati (es. Hadoop, Cassandra, Kafka) |
| **Spread** | Ogni istanza su rack hardware distinto con rete e alimentazione propria. Max 7 istanze per AZ per gruppo | Riduce failure correlati per applicazioni critiche |

Limitazioni (dal Dojo):
- Non puoi unire placement groups
- Un'istanza non può essere in più placement groups
- Non puoi lanciare Dedicated Hosts in placement groups
- Un **cluster placement group non può estendersi su più AZ**

## Auto Scaling — In Profondità (dal PACKT, Kimiko, Dojo)

### I 3 Componenti di Auto Scaling (dal Dojo)

Il Dojo identifica tre componenti principali:

1. **Auto Scaling Group**: unità logica per scaling e gestione. Ha min, max e desired number di istanze
2. **Configuration Template**: launch template (raccomandato) o launch configuration. Contiene AMI ID, instance type, key pair, security groups, block device mapping. Il Dojo nota: *"È raccomandato usare un launch template piuttosto che una launch configuration, perché quest'ultima offre solo feature limitate."* Con i launch template puoi avere **multiple versioni** e **multiple instance types con diverse purchase options**
3. **Scaling Options**: dynamic, predictive, o scheduled

### Horizontal vs Vertical Scaling (dal Dojo)

- **Horizontal Scaling**: aggiungi più server. Workload distribuito. Serve Auto Scaling + ELB. *"Ottimo per server stateless come web server pubblici"* (Dojo)
- **Vertical Scaling**: aumenti risorse di un singolo server (CPU, RAM). *"Adatto per risorse stateful o operazioni difficili da gestire in modo distribuito, come write query su database"* (Dojo). Per EC2 e RDS, l'istanza deve essere fermata prima di modificare la dimensione

### Instance Warm-up e Cooldown (dal Dojo)

- **Instance warm-up**: *"Il processo di lancio non è istantaneo. AWS deve recuperare l'AMI, fare la configurazione, eseguire lo user data, installare le applicazioni custom"* (Dojo)
- **Cooldown**: *"L'intervallo tra due azioni di scaling. Previene conflitti dove un'attività aggiunge istanze mentre un'altra le termina"* (Dojo)
- **Termination policy**: controlla quali istanze vengono terminate per prime durante scale-in (Dojo)

### Health Check con Load Balancer (dal Dojo)

Il Dojo nota: *"Quando associ un load balancer all'ASG, dovresti usare l'health check del load balancer per il monitoring. Quando un'istanza è considerata unhealthy dall'health check del LB, inizierà un evento di scaling per sostituire l'istanza difettosa."*

### Auto Scaling Groups — ASG (dal PACKT)

Il PACKT descrive gli ASG come *"collezioni di istanze EC2 che condividono caratteristiche simili e servono uno scopo comune. Gli ASG ti permettono di specificare capacità minima, massima e desiderata."*

### Scaling Policies (dal PACKT e Dojo)

Il Dojo fornisce i dettagli sui 3 tipi di scaling policy:

**Simple Scaling** (dal Dojo):
- Basato su una singola metrica (es. CPU > 80% → aggiungi 20% capacità)
- *"Quando EC2 Auto Scaling fu introdotto, questa era l'unica policy supportata. Non fornisce controllo fine-grained."*
- Deve aspettare che gli health check completino e il cooldown scada prima di rispondere a un altro allarme

**Target Tracking** (dal Dojo):
- Specifichi una metrica e un valore target che l'ASG deve mantenere sempre
- Esempio: *"La metrica è average CPU utilization, il target è 80%. Quando CloudWatch rileva che la media è sopra 80%, triggera la policy per scalare out. Quando scende sotto 80%, scala in."*
- Limitazione: *"Scala out proporzionalmente alla metrica il più velocemente possibile, ma scala in più gradualmente"*
- Metriche predefinite: `ASGAverageCPUUtilization`, `ASGAverageNetworkIn`, `ASGAverageNetworkOut`, `ALBRequestCountPerTarget`

**Step Scaling** (dal Dojo):
- Migliora il simple scaling con **step adjustments** — azioni diverse in base alla dimensione della breach
- *"Con step scaling, la policy può continuare a rispondere ad allarmi aggiuntivi anche nel mezzo di un evento di scaling"* (a differenza del simple scaling)
- Esempio dal Dojo: CPU 40-60% → mantieni. CPU 60-70% → +10%. CPU >70% → +30%. CPU 30-40% → -10%. CPU <30% → -30%

Metriche comuni per lo scaling (dal PACKT):
- **CPU utilization** — per applicazioni CPU-bound
- **Network traffic** — per applicazioni con attività di rete variabile (web server, API)
- **Custom application metrics** — response time, queue length, qualsiasi metrica indicativa delle performance

### Scaling Actions (dal PACKT)

- **Launching new instances**: in risposta a domanda aumentata
- **Terminating instances**: quando la domanda diminuisce, per ridurre costi
- **Timeout parameter**: evita scaling costante su spike improvvisi. *"Non ha senso provisionare una nuova istanza se, quando viene online, le metriche di traffico sono tornate sotto la soglia"*
- **Cooldown policies**: fermano ulteriore scaling per un periodo (es. 5 minuti)

### Predictive Scaling (dal PACKT)

*"Il predictive scaling è una feature avanzata che sfrutta algoritmi di machine learning per prevedere la domanda futura basandosi su pattern storici."* Esempio: un'azienda di contabilità è più occupata negli ultimi giorni di ogni mese. Il predictive scaling impara questo pattern e inizia a scalare prima che la domanda cresca.

### Lifecycle Hooks (dal PACKT)

Permettono azioni custom durante il lancio o la terminazione di istanze:
- Prima della terminazione: shutdown graceful per evitare perdita dati
- Prima di ricevere traffico: health check e validazioni di readiness
- Prima del servizio: inizializzazione impostazioni (es. leggere parametri da Parameter Store o Secrets Manager)

## High-Performance Compute (dal PACKT Cap.14)

### Decoupling per Scaling Indipendente (dal PACKT Cap.14)

Il PACKT Cap.14 spiega: *"In un'applicazione web containerizzata, il frontend web può essere scalato separatamente dai container che gestiscono la logica applicativa. Questo permette maggiore scalabilità del frontend durante periodi di alto traffico, anche se il layer applicativo rimane invariato."*

### Scegliere il Tipo di Istanza Giusto (dal PACKT Cap.14)

Il PACKT Cap.14 fornisce linee guida:
- **Alta potenza di processing** → Compute-optimized (C6i) per batch processing e HPC
- **Molta memoria** → Memory-optimized (R6g) per database in-memory e analytics real-time
- **AI/ML** → Tranium e Inferentia instance types
- **Alto disk throughput** → Storage-optimized (I3) per data warehousing e file system distribuiti

> **Tip esame (PACKT Cap.14)**: *"You may be expected to know what each of the instance family types are optimized for, so try to have a high-level understanding of each of the families."*

### Enhanced Networking (dal Dojo)

Il Dojo menziona feature di networking avanzato:
- **Elastic Network Adapter (ENA)** — per networking ad alte performance
- **Intel 82599 Virtual Function (VF)** — interfaccia alternativa
- **Elastic Fabric Adapter (EFA)** — per workload HPC e ML, throughput di rete superiore al TCP standard

## Scenari Tipici d'Esame

### Scenario 1: Workload interrompibile a basso costo
**Domanda**: Hai un job di batch processing che può essere interrotto. Come risparmiare?

**Risposta**: **Spot Instances** — fino a 90% di sconto, con 2 minuti di preavviso (Dojo).

### Scenario 2: Workload steady-state per 3 anni
**Domanda**: Un'applicazione gira 24/7 con carico prevedibile per i prossimi 3 anni.

**Risposta**: **Reserved Instances** o **Savings Plans** per 3 anni con pagamento upfront per massimo sconto (PACKT, Dojo).

### Scenario 3: Bassa latenza tra istanze
**Domanda**: Un cluster HPC richiede la minima latenza possibile tra le istanze.

**Risposta**: **Cluster Placement Group** nella stessa AZ (Dojo).

### Scenario 4: Storage ad altissime IOPS temporaneo
**Domanda**: Serve storage con le IOPS più alte possibili, i dati non devono persistere.

**Risposta**: **Instance Store** (Dojo: *"Instance store volumes are physically attached to the EC2 instances, so your instances are able to access the data much faster"*).

### Scenario 5: Licensing per-socket
**Domanda**: L'azienda ha licenze software per-socket che deve portare nel cloud.

**Risposta**: **Dedicated Hosts** — supporta BYOL con visibilità su socket e core (Dojo).

### Scenario 6: Scaling predittivo
**Domanda**: Un'applicazione ha pattern di traffico prevedibili (picchi a fine mese).

**Risposta**: **Predictive Scaling** con Auto Scaling (PACKT: *"Predictive scaling can learn this pattern and start to autoscale before demand grows"*).

## Riepilogo Veloce per l'Esame

- **Instance families**: General (T/M), Compute (C), Memory (R/X), Storage (I/D), Accelerated (P/G), HPC (PACKT, Dojo)
- **Burstable (T)**: CPU credits, monitora per evitare degradazione (PACKT)
- **Nitro**: fino a 64,000 IOPS per volume EBS (Dojo)
- **Instance Store**: temporaneo, IOPS più alte, dati persi allo stop (PACKT, Dojo)
- **EBS**: persistente, network-attached, snapshot possibili (PACKT)
- **On-Demand**: nessun impegno. **Spot**: fino a -90%, interrompibile. **RI/Savings Plans**: impegno 1-3 anni (Dojo, Kimiko)
- **Savings Plans**: più flessibili delle RI. Compute SP si applica anche a Fargate e Lambda (Dojo)
- **Standard RI**: vendibili su Marketplace. **Convertible RI**: cambi attributi ma non vendibili (Dojo)
- **Dedicated Hosts**: BYOL, visibilità hardware. **Dedicated Instances**: isolamento senza visibilità (Dojo)
- **Placement Groups**: Cluster (bassa latenza, stessa AZ), Partition (failure isolati, max 7/AZ), Spread (rack distinti, max 7 istanze/AZ) (Dojo)
- **Auto Scaling**: 3 componenti (ASG + template + scaling options). Launch template > launch configuration (Dojo)
- **Horizontal = più server (stateless), Vertical = più risorse (stateful)** (Dojo)
- **Warm-up**: tempo per preparare l'istanza. **Cooldown**: intervallo tra scaling actions (Dojo)
- **ASG + LB**: usa health check del LB per sostituire istanze unhealthy (Dojo)
- **Lifecycle Hooks**: azioni custom prima di servire traffico o prima della terminazione (PACKT, Dojo)
- **EFA**: per HPC e ML, throughput superiore a TCP (Dojo)
